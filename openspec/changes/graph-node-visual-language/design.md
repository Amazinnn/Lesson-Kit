## Context

只需要解释方案所必需的现状（动机见 `proposal.md` 的 Why）：

1. **相机是唯一的缩放来源，且它把排版单位一起缩小。**
   `.graph-stage` 上一个 `transform: translate(...) scale(s)`
   （`workbench/server/static/workbench.js:1106`）作用于**整棵子树**；
   而 `--size`（`workbench.js:1309`）、`.node-value` 的 `clamp(11px, size*.28, 18px)`
   （`workbench.css:1690`）、`.label` 的 `12px`（`workbench.css:1711`）、
   `.node-satellite` 的 `7px`（`workbench.css:1694`）**全是世界像素**。
   〔实证〕Fit 后 `s = 0.17–0.49` ⇒ 圆直径 3–30px、标签 2.0–5.9px、可见标签 0–1/31
   （`workbench.css` 与 `workbench.js:1222-1225` 的离线复算，见审计 §7.3）。
2. **节点是五层叠一个圆。** `.metric-track`（度量弧）+ `.status-ring`（状态环）+
   `.node-face`（面）+ `.node-value`（数字）+ `.node-satellite`（状态点）
   （`workbench.js:957-1053` 的 DOM 结构），加下方 `.label` 与 `.meta`。
   〔实证〕`.status-ring` 的唯一变色分支 `.node-wrap.in-scope .status-ring`
   （`workbench.css:1708`）**永不命中** —— `graphSyncScope()`（`workbench.js:1077`）
   是空函数；`.node-wrap.warning`（`workbench.css:1653`）也没有任何 JS 会加。
3. **同环两维度。** 弧长 = 当前投影指标（`workbench.js:1067` 写 `--metric-angle`），
   弧色 = 知识点重要度（`workbench.css:1651-1652` 的 `--kind-color`）。
4. **学习状态实质不可辨。** 唯一在线通道是 7px 世界像素的卫星点，
   而 28/31 个节点同为 `state-new`（同一个灰 `#9da4ae`）。
5. **图谱自有 token，且与全站零耦合。** 12 个**裸名**变量声明在 `:root`
   （`workbench.css:1505-1518`）；〔实证〕图谱区段 `:1497-1884` 对
   `var(--lk-*)` / `var(--dsw-*)` 的引用 **0 次**，且这 12 个裸名在区段外的引用
   也 **0 次**（`awk 'NR<1497||NR>1884' workbench.css | grep -cE
   'var\(--(paper|ink|hair|blue|blueSoft|yellow|yellowSoft|red|redSoft|green|graphite|shadow)\b'` → 0）。
6. **图例与实况不符。** 图例「相关」色 `#aaa399`（`workbench.css:1796`），
   WebGL 实际线色 `rgb(117,112,104)` = `#757068`（`graph-renderer.js:15-21`）。
7. **底噪是每帧 600 个 alpha 混合光斑**（`workbench.js:1482-1488`、`:1538-1626`），
   与数据无关，只在节点周围挖洞（`:1515-1530`）。
8. **图例／图谱外壳是服务端渲染的**（`workbench/server/pages.py:410-481`），
   节点是 DOM（可访问、可交互），关系线是 WebGL2 canvas。

## Goals

- **让图谱在任意画布尺寸下可读**：节点的绘制尺寸、字号、线宽用**屏幕像素**表达，
  Fit 后不再是 3–14px 的斑点（复核 `proposal.md` 的 Why）。
- **给节点一套自有视觉语言**：同心圆形态、收窄的连续尺寸映射、四个投影各自的色键、
  随投影切换的图例、常态可见但降对比度的标签。
- **让学习状态在图上可辨**，且**不靠颜色单独承载**（G-6 + G-21 + 冗余状态通道）。
- **夜纸下图谱跟随夜纸**（A-7 / A-8 / G-19），图谱自有一套夜纸值集。
- **只改外观**：布局、关系、交互、后端、图谱以外的任何东西都不动。

## Non-Goals

- 不改布局物理：力模型、吸引强度、端口与车道、24px 逻辑间距、Worker 求解流程
  （`graph-physics-core.js` / `graph-physics-worker.js`）语义不变。
  **唯一的例外是节点尺寸映射的取值区间**（G-17 明确授权）。
- 不改关系线的线型、粗细、透明度、箭头方向、绘制顺序（亮色主题下**逐值不变**）。
- 不改交互：搜索、筛选、缩放、平移、Fit、拖拽、聚焦、聚拢滑杆、详情看板。
- 不改投影语义：四个投影分别代表什么、各自的数值来自哪个字段，一律不变。
- 不新增任何后端字段、不新增任何学习事实、不改 API 与 CLI。
- 不碰图谱以外的任何页面。
- 不动 `openspec/changes/workbench-visual-language-v2/` 下的任何文件。

## Decisions

### D-1 屏幕空间缩放补偿（**最高优先级，G-24**）

**决策**

把节点的**绘制几何**从「世界像素」改成「**屏幕像素**」：
`scale()` 只负责**位置**，节点的直径、字号、环宽**不再随相机缩小**。三个数值：

1. **绘制半径（屏幕 px）** = `20 + 24·√score`（G-17 的量程，G-24 的单位），
   `score` = 现有的 `GraphPhysics.scoreFor(node)`（`graph-physics-core.js:1463-1470`）。
   **它是当前投影的量到半径的连续映射，单位是屏幕像素，且与相机缩放无关** ——
   缩放只改变节点之间的**间距**，不改变节点本身的大小。
2. **世界尺寸**（物理用的 `node.size`）= 同一个函数，单位换成世界 px
   ⇒ 直径 40–88 世界 px（现状 `sizeFor()` 是 20–80 世界 px，
   `graph-physics-core.js:60-61`）。
   物理、footprint、碰撞、端口间隙**全部照旧**，只是量程变了（G-17）。
3. **排版与线宽全部屏幕化**：`.label` 11px、圆心数字 `clamp(12px, .34·D, 18px)`、
   外环线宽 1.5–4 屏幕 px（随量值，D-3）、节点与标签的间距 8px
   —— 全部用 `calc(<px> * var(--inv-scale))`
   写在**舞台坐标**里。`--inv-scale = 1 / var(--stage-scale)`，
   而 `--stage-scale` 由 `graphApplyView()`（`workbench.js:1104-1107`）在写 `transform`
   的**同一次调用**里写到 `.graph-stage` 上。**一次相机变化 = 一次变量写入**，
   不引入任何新状态、不引入逐节点的 JS 计算。
4. **实现落点**：JS（`graphPaintNodes()`，`workbench.js:1296-1325`）每帧写两个值：
   `--node-d`（屏幕 px 的绘制直径，供字号换算）与 `--node-box`（舞台 px 的盒子尺寸
   = `--node-d / s`）。盒子是透明的，只承载命中区与两个子层的定位；
   **命中区 = 绘制直径**（视觉与手感一致）。

**理由**

- G-24 的依据就是这个：*「现状 Fit 后 scale = 0.17–0.49，圆直径仅 3–30px、
  标签 2.0–5.9px、可见标签 0–1/31 —— 在这个尺寸上，新的配色与同心圆根本看不出来。」*
  不先修补偿，后面的同心圆、暖色板、图例都白做。
- 「绘制层用屏幕像素、世界层用世界像素」是唯一能同时满足三件事的做法：
  ① 物理与布局**零改动**（G-10）；② 排版、线宽、数字在任意缩放下**恒定可读**；
  ③ 节点的**相对大小**（量值感）仍在 —— 它由同一个 `scoreFor()` 连续映射而来。
- 〔推断〕G-17 的「20 → 44px」与 G-24 的「按屏幕像素」只有一种自洽的合读：
  **半径区间 20–44，单位是屏幕像素**。这也与「缩放不该把节点缩小」的直觉一致。

**关键数字（〔实证〕离线复算 dmath/ch06，31 节点）**

| 画布（CSS px） | 现状 scale | 现状圆直径 | 现状标签字号 | 现状可见标签 | **新圆直径** | **新标签字号** | **新可见标签** |
|---|---|---|---|---|---|---|---|
| 860 × 460 | 0.37 | 7–30px | 4.4px | 1 / 31 | **40–88px** | **11px** | 全部渲染，重叠者让位 |
| 1140 × 600 | 0.49 | 10–39px | 5.9px | 12 / 31 | **40–88px** | **11px** | 同上 |
| 703 × 372 | 0.29 | 6–23px | 3.5px | 0 / 31 | **40–88px** | **11px** | 同上 |
| 411 × 230 | 0.17 | 3–14px | 2.0px | 0 / 31 | **40–88px** | **11px** | 同上 |

> 新三列与相机无关：绘制尺寸是屏幕像素，标签同理。
> 唯一随画布变化的是**节点的间距**（世界布局 × scale）与**拥挤度**（见 Risks R-1）。

**否掉的备选**

- **A. 把整个舞台的 `scale()` 去掉，改成 JS 逐节点换算屏幕坐标。**
  否掉：等于重写渲染栈（WebGL 画布在舞台内、`stageScale()` 反解变换、
  `routePath` 在世界空间），而 `calc()` 补偿能得到同样的像素结果。
- **B. 绘制半径 = 世界半径 × s（只把「过小」的部分抬到下限）。**
  否掉：这样**量值差会在低缩放下被压平**（G-17 的「量值感更强」落空），
  而且它读不出 G-17 的「20 → 44」这组数字。**本设计采用字面读法。**
- **C. 标签保持世界像素（不补偿），只补偿圆盘。**
  否掉：标签才是「看不清」的主因（2.0–5.9px）。
- **D. 把标签移出舞台，单独做一个屏幕空间图层。**
  否掉：可行但要动 DOM 归属与命中区；`calc()` 补偿能得到同样的像素结果。

**代价**

- 世界层的 `labelWidth()`（`graph-physics-core.js:82-85`，按 **12px/字符**估算）
  与屏幕层 11px/字符的**实际标签宽度**在低缩放下不再匹配
  （s≈0.4 时实际标签的世界占位约为模型估算的 2.5 倍）。
  ⇒ 由 **D-6 的屏幕空间重叠让位**兜底，**不**改 `labelWidth()`
  （改了就是改布局物理）。
- **绘制圆盘比布局给它的位置大**（屏幕像素的圆 vs 世界像素的预留）⇒
  Fit 视图下相邻圆盘会压盖。〔实证〕860×460 下圆盘面积占节点簇面积约 **47%**。
  这是「屏幕像素半径 20–44」在当前中栏宽度下的直接后果，缓解手段见 **Risks R-1**。
- 缩放变成纯粹的「拉开间距」：放大时节点**不变大**，只是彼此远离
  （D-11.4 交代了工具条文案）。

### D-2 同心圆结构：内核淡 + 外环深

**决策**

节点由**两件**构成，取代现在的五层：

| 层 | 元素 | 视觉 | 承担什么 |
|---|---|---|---|
| **内核** | `.node-core`，`border-radius: 50%` | 同色相的**淡**填充（色相混纸 20%） | 圆片的「面」；让节点有实体感（现状 `.node-face` 填充 58% 之外是纯 `--paper`，等于没有实体） |
| **外环** | `.node-ring`，`border-radius: 50%` + `border` | 同色相的**实**色环，线宽 1.5–4 屏幕 px（随量值，D-3） | 节点的**边界**；承载该投影的颜色与量值；关系线接在它的外缘（D-7）；选中时再加粗变实（G-15） |

- 圆心只放**一个数字**：该节点的**正式题数**（G-9 的字面读法：「**只留一个题数数字**」）。
  **所有投影下都是同一个数** —— 投影的量由**大小 + 环宽 + 颜色**承载，
  圆心不再随投影变化（这同时让 G-6 成立：「学习状态」投影下不再需要写入「练/复/熟/新」）。
  数字压在内核之上（`z-index` 在内核之上，且**不得**溢出外环的内缘）。
  〔依据〕`node.problems` 已是**正式题数**（`review-workbench` 的 `Semantic graph attraction`：
  「Only formal problems contribute to problem counts」）。
- **绘制层级**：`内核` → `数字` → `外环`（外环最后画，保证边界线不被内核压住）；
  三者都在 `.node` 盒内，`.node` 盒的尺寸 = 屏幕直径（`--node-box`）。
- **外环的半径 = 盒子的外缘**（`inset: 0` + `box-sizing: border-box`），
  内核半径 = 盒子半径 − 环宽。
- 现状的 `.metric-track`、`.status-ring`、`.node-satellite` **全部删除**（D-10）。

**理由**

- G-1 原文：「**两个有层次的同心圆**（内核 + 外环），取代现在『五层信息挤在一个圆里』」。
- G-13 原文：「**内核淡、外环深**（同一色相两档）。内核最轻、外环最实，
  节点读作一枚带边的圆片」——「读作一枚带边的圆片」正是本决策要造出来的形状。
- 内核给实体、外环给边界，是唯一能同时满足「有体积」与「有可读的边界色」的组合；
  现状两者都缺（填充=纸色、边框 1px 被缩到 0.37px 亚像素）。

**否掉的备选**

- **单层实心圆 + 一道描边。** 否掉：G-1 明确要「两个有层次的同心圆」；
  且单层无法同时表达「色相族」与「该投影的分类/量值色」。
- **内核深、外环浅。** 否掉：G-13 明确「内核淡、外环深」；
  且边界色必须是**对比度 ≥3:1** 的那档，浅环读不出边界。

**代价**

- 节点比现在多一个 DOM 元素（31 节点 = 多 31 个 span）——可忽略。
- 外环粗细**同时**承载量值（D-3）与选中强调（D-8）⇒ 选中态必须在量值基线之上**再加**，
  并靠「变实」（颜色走到最实的一档）区分，否则两个读数会互相污染。

### D-3 尺寸映射：连续、收窄、半径 20→44 **屏幕像素**（外环粗细同源）

**决策**

- **绘制半径**（屏幕 px）= `20 + 24·√score`（D-1），连续、单调，区间 20 → 44。
- **外环线宽**（屏幕 px）= `1.5 + 2.5·score`，与半径**同源**（同一个 `score`）。
  ⇒ 一个量值有三条通道：**半径、外环粗细、颜色**。
- **世界尺寸**（物理用的 `node.size`，世界 px）= `2 × (20 + 24·√score)` = 40–88。
  现状是 `sizeFor() = 20 + 60·√score`（直径 20–80，即半径 10–40）
  ⇒ **区间 30 → 24（收窄 20%）、最小值翻倍、最大值 +10%**。
  物理、footprint、碰撞、端口间隙**全部照旧**，只有量程变（G-17）。
- 映射函数保持 `√`：〔实证〕现状注释（`graph-physics-core.js:48-59`）说明
  开平方是为了让中低分区间也够得着；换掉它会改变现有分布形状。
- **选中/悬停不再独占环宽**：它们在量值基线之上**再加**粗（D-8），
  于是「当前量值」与「当前选中」两个读数不冲突。

**理由**

- G-3：「连续映射但**收窄范围**（保留『题数多则大』，但半径区间收窄，避免看起来随机）」；
  G-17：「**20 → 44px**（比现状更强调，量值感更强）」。
  收窄 30→24 + 最小值翻倍 ⇒ 同一批节点的**相对差异不变、绝对差异更易读**。
- G-2 的原话是「用**颜色与大小**表意即可」——「大小」含半径与环宽两维，
  两者都取自同一个 `scoreFor()`，是同一份信息的两个刻度，不是两个维度。
- 环宽承载量值不与 G-15 冲突：G-15 的「外环加粗变实」是**在基线之上再加**，
  且带「变实」（颜色走到最实的一档）这个第二信号。

**度量弧被删之后，信息没有丢——逐项核对**

| 弧原来承载的 | 现在由谁承载 | 是否丢失 |
|---|---|---|
| 弧长 = 当前投影指标的归一化值 | **半径 + 外环粗细**（同一个 `scoreFor()`，同一个单调映射） | 不丢（半径与环宽本来就是量值通道） |
| 弧色 = 知识点重要度（core 蓝 / support 黄） | **无** | **丢**，见下 |
| 弧起点 215°、302° 弧长的固定缺口 | 无 | 不丢（纯装饰，读不出信息） |

〔推断〕**core / support 的视觉区分在四个投影中全部消失**。这是 G-2 的既定代价
（原话：「用颜色与大小表意即可」）。它的语义仍由「重要性」投影承载：
`importance` 投影的**量值**（`importance` 本身，`workbench.js:1059` 的
`Math.round(node.importance * 100)`）决定该投影下节点的大小、环宽与色阶
（`kind` 由 `importance` 派生，`workbench.js:866`）⇒ 重要度**仍在图上可读**，
只是不再有独立的蓝/黄两色。〔待核〕实现时确认 `kind` 与 `importance` 的取值关系。

**否掉的备选**

- **线性映射**（`R = 20 + 24·score`）：低端节点全挤在 20px，量值感尽失。
- **保留弧、改成实心圆环**：G-2 已裁定「移除」。
- **环宽不承载量值（恒定 2px）**：会让「大小」只剩半径一维，且与
  `Metric projection morphology` 的「a thicker node outer ring」不一致。

**代价**

- 世界节点变大（直径 20–80 → 40–88）⇒ footprint 变大 ⇒ Fit 缩放略降

### D-5 每个投影一套色键 + 图例随投影切换

**决策**

| 投影（`pages.py:411-412`） | 节点色键 | 性质 | 依据 |
|---|---|---|---|
| 关系结构 `structure` | **墨阶三档**（外环 / 数字 / 内核） | 颜色**不承载语义**；关系由边的线型承载 | G-22 |
| 题目数量 `problem_count` | **量值橙阶 4 档** | 单色阶 | G-12 / G-20 |
| 重要性 `importance` | **量值橙阶 4 档**（与上一行同一套） | 单色阶 | G-12 / G-20 |
| 学习状态 `state` | **状态四色** | 分类色 | G-12 / G-21 |

- 〔推断〕两个**量值**投影共用同一套橙阶：G-12 的规则是「量值型投影用同一色相的
  明度阶」，两者都是量值型；用颜色把「题数」和「重要性」区分开反而违反该规则。
  两者的区别由**顶栏 Tab**（投影名）与**图例下半块**（当前投影的值说明）承担。
- **分档规则**：把归一化值 `score`（`scoreFor()`，0..1）切成 4 档
  （`score < .25` / `< .5` / `< .75` / 其余），取对应色阶。
  〔待核〕分档阈值在实现时用 dmath/ch06 的真实分布校验，避免某一档空置。
- **图例改两块**（G-14）：
  - **上半：关系线型** —— 现状的 5 项（先修 / 相关 / 应用 / 对比 / 隐含），
    保留可点按显示/隐藏的行为（`pages.py:462-467` 的 `data-edge-type` + `aria-pressed`），
    只把「相关」色改成实况值 `#757068`（D-10）。
  - **下半：节点颜色键** —— **随当前投影切换**。
    - 分类投影（学习状态）：4 个色块 + 状态名（未学 / 复习 / 掌握 / 需突破）。
    - 量值投影（题目数量 / 重要性）：4 个色块 + 档位（低 → 高）+ 一行
      「数字 = 该节点的正式题数；大小与环宽 = 当前投影的量」。
    - 关系结构投影：颜色**不承载语义**（G-22），所以下半块显示**节点结构键**
      （一枚样例节点 + 外环 / 内核 / 数字三件的说明），而不是色阶列表。
      〔推断〕这是 G-11「什么颜色对应什么类型」在「颜色无类型」这一投影下的唯一诚实表达。
- **实现**：下半块的 4 套内容在 `pages.py` 里**一次渲染全**，
  每套带 `data-legend-for="structure|problem_count|importance|state"`，
  由 `graphApplyView()` 切换可见的那一套（与顶栏 Tab 的 `data-view` 同源）。
  颜色值只在 CSS 里定义一处，模板只给结构 ⇒ 不会两处漂移。

**理由**

- G-8：「不同类型的图谱，配色不同（4 个投影各有自己的色键）」；
  G-14：「底部图例分两块 —— 上半是关系线型（保留现状），下半是节点颜色，随当前投影切换」。
- 现状的图例**只解释关系、不解释节点**（`pages.py:462-467` 全是关系类型），
  于是「蓝弧黄弧、灰点、数字」无从解读（审计归因 10）。

**否掉的备选**

- **一个全局色板 + 切换投影只改数字**：否掉，G-8/G-11 已裁定每投影一套。
- **图例只画色块、不写字**：否掉，G-11 要求「什么颜色对应什么类型」；
  且状态色与全站角色色不同（图谱自有色板），没有文字就无从对照。

**代价**

- 图例高度随投影变化（4 项 / 4 项 / 4 项 / 一枚节点图）⇒ 需要预留固定高度，
  避免切换时画布抖动。
- `pages.py` 的图例结构从 5 项变 5 项 + 4 套键 ⇒ 服务端模板变长。

### D-6 标签系统：常态可见、降对比度、重叠让位

**决策**

1. **常态可见**（G-5）：标签默认渲染，**不再按缩放阈值隐藏**。
   现状的 `LABEL_MIN_RADIUS_PX = 14` 与 `labelScaleThreshold()`
   （`workbench.js:1290-1294`）+ `labelVisible` 判定（`:1319-1321`）**删除**；
   〔实证〕这条规则在 Fit 后（s = 0.17–0.49）让 30/31 个节点没有标签。
2. **字号与对比度**：**11 屏幕 px**（D-1 的 `calc(11px * var(--inv-scale))`），
   颜色 `#5c5549`（亮纸 7.24:1）/ `#c9c2b5`（夜纸 9.82:1）——
   比现状的 `#2b2925`（≈15:1）**明显降一档**，但仍 ≥4.5:1（G-5「降低对比度不抢节点」）。
   圆内数字（12–18 屏幕 px，内容恒为该节点的正式题数）是**更响**的一层，层级由此拉开。
3. **换行而非截断**：`.label` 保持 `max-width` 语义（现状 `168px`，`workbench.css:1711`）
   并**按屏幕像素补偿**（`calc(168px * var(--inv-scale))`），
   **不加** `text-overflow: ellipsis`、**不加** `-webkit-line-clamp`。
   〔实证〕现状本来就没有省略号（`workbench.css:1710-1715`），文字是**换行**的。
4. **重叠让位**（G-23）：新增一个**屏幕空间**的去冲突 pass：
   - 触发时机：相机变化（缩放/平移）、布局收敛、投影切换、选中变化 —— **不是每帧**。
   - 排序（谁让谁）：**半径降序 → 重要度降序 → 节点 id 升序**（确定性）。
   - 规则：标签矩形相交时，**排位靠后者隐藏**（`opacity: 0` + `aria-hidden`）。
   - **可见标签预算**：即使不重叠，同时绘制的标签也有上限。
     预算 = `floor(画布面积 / 9000)`（一个标签块 ≈ 66×30 屏幕 px，留一倍呼吸空间），
     860×460 ⇒ 43；dmath/ch06 的 31 个节点不会触顶，**大章节**（100+ 节点）会。
     超预算时按同一排序保留前 N 个。
   - **永不隐藏**：选中节点、悬停节点、其 1 跳邻居（与既有契约
     `workbench-ui:248`「selected, hovered, and high-focus labels SHALL remain visible」一致）；
     被隐藏的标签在**悬停/选中该节点时立刻恢复**（`opacity` 回到 1）。
   - 被隐藏者的**完整标题**仍在悬浮提示（`label.title = node.title`，
     `workbench.js:996`）与学习看板里可得。
5. **状态文字从节点上消失**（G-6）：
   - 删除 `.meta` 行（内容由 `workbench.js:1072-1073` 写入「状态标签 · 投影名 值」）；
   - 删除「学习状态」投影写入圆心的单字「练/复/熟/新」
     （`STATE_SHORT`，`workbench.js:578`；写入点 `workbench.js:1060`）——
     圆心恒为**正式题数**（G-9），四个投影都一样。
   - 状态名仍保留在：**学习看板**（`pages.py:474-477`）、
     `button.title` / `label.title`（悬浮）、`aria-label`（`workbench.js:973`）。

**关于「完整文本」的契约漂移（显式登记）**

〔实证〕`workbench-ui:471-473` 写的是「Node labels SHALL always display their complete
text — wrapping to multiple lines instead of truncating」，
但实现里 JS 会把标题在**第一个标点处截断**（`graphTitleCut`，`workbench.js:806-817`），
标签显示的是**简称**。这是既有的**契约漂移**。
本变更**不删简称**（删了会让标签长 2–3 倍，且 `labelWidth()` 依赖 `shortTitle`
⇒ 改布局物理，越界），而是**在 `workbench-ui` 的 delta 里把条款限定为
「标签**显示时**呈现的是它自己的完整文本，无省略号、无字符上限，换行而不截断；
节点的完整标题由悬浮与键盘聚焦承载」**——与并行产出的 delta
（`specs/workbench-ui/spec.md` 的 `Living graph motion and readable labels`）一致。

**否掉的备选**

- **保留缩放阈值隐藏，只把阈值调低**：否掉，G-23 明确「**不靠缩放**」；
  且阈值规则与屏幕像素字号互斥（有阈值就必然有「看不见的标签」）。
- **两行截断（`-webkit-line-clamp: 2`）**：与 `workbench-ui:471-473` 冲突，且
  G-5 的原话是「截断改两行**或**悬浮显示全文」——选了后者。
- **标签随缩放一起变大（不补偿）**：那就回到 D-1 的问题。
- **去冲突 pass 在世界空间做**：世界空间不随相机变化，屏幕空间才是「重叠」的真实判据。

**代价**

- 需要一次标签矩形测量（`getBoundingClientRect`）⇒ 必须**批量读**（一次读全部），
  否则触发强制回流。31 个节点 × 一次批量读，可接受。
- 标签在低缩放下占的世界空间是模型的 ~3 倍 ⇒ 视觉上标签会盖住邻点的圆盘。
  〔推断〕为避免"标签压住别人的圆"，去冲突 pass 同时判定
  「标签矩形 ∩ 邻点圆盘」——命中且该邻点未被隐藏时，**先藏标签**（标签让位于节点）。
- 简称仍然是简称（漂移已登记，未解决）。

### D-7 关系线端点接到外环边缘（WebGL 端点计算）

**决策**

- 现状：物理核心用 `endpointRadius(node)`（`graph-physics-core.js:1345-1347`）=
  `size × (1 − 2×.07)/2 − 1`，即旧 `.node-face`（`inset: 7%`）的可见半径。
  〔实证〕该常量 `NODE_FACE_INSET = .07`（`:1343`）**与 CSS 的 `inset: 7%`
  是一对-coupled 的**，注释明说「If the face's inset ever changes, this constant
  has to change with it」。
- 新形态下 `.node-face` 与 `inset: 7%` 都不存在了 ⇒ `NODE_FACE_INSET` 与
  `endpointRadius` **必须重写**：端点半径改为**外环的外缘**，
  即世界半径 `R_outer_world = R_screen / s`（`R_screen` = D-1 的绘制半径，
  20–44 屏幕 px；`s` = 舞台缩放）。
- **实现位置在渲染层**：`graph-renderer.js` 已经读得到缩放
  （`var scale = stageScale(stage)`，`:267`），且路径已经被采样成 16 段
  （`:283-300`）。做法：
  1. 渲染器按**采样点**从两端向节点中心回退，直到与节点中心的距离 ≥ 新的端点半径，
     再从那里开始/结束画；
  2. 新的端点半径由一个**共享函数**给出（见下）。
- **共享函数**（避免两处漂移）：在 `graph-physics.js` 的门面
  （`workbench/server/static/graph-physics.js`，现有门面在 `:214-300`）上新增
  `nodeScreenRadius(node)`，**同时**被 `workbench.js`（画节点）与
  `graph-renderer.js`（修端点）使用。〔实证〕两端必须用同一个公式，
  否则线会与圆盘错位（线头露在环外，或线头缩进环内）。

**理由**

- G-18 原文：「**接到外环边缘**。这是节点改形的**必要连带修改**
  （会动到 WebGL 端点计算），但关系线本身的线型、粗细、颜色不改」。
- 屏幕像素的绘制圆盘（D-1）**永远比逻辑 footprint 大**（两者单位不同）⇒
  端点若仍按逻辑半径算，线会**停在圆盘里面**，肉眼可见地「够不着节点」。

**否掉的备选**

- **把缩放推进物理核心（Worker 知道 scale）**：否掉 —— 布局会随缩放变化 ⇒
  缩放会 reheat 求解器，违反 `workbench.js:1107-1108` 的
  「Camera movement never reheats the solver」与 `workbench-ui:155-158`
  「Fit without rewriting layout」。
- **端点保持旧半径，靠外环盖住缺口**：缺口是 `R_screen − R_world·s` 屏幕 px
  （在 Fit 视图下可达 15–25px）—— 环宽 1.5–4px 盖不住，会露出一截短线。
- **把关系线画在节点之上**：会破坏「关系由线型承载」的可读性，也与
  现状 z-index（关系线 canvas = 1，`graph-renderer.js:147`；节点 = 2，`workbench.css:1646`）相反。

**代价**

- 渲染器多一段端点回退逻辑（约 20 行），且必须与画节点的公式共用同一实现。
- 边被**截短**一小段（端点从旧半径退到新外缘）⇒ 关系线的**可见长度**略变，
  但**几何拓扑不变**（同一对端点、同一控制点族）。

### D-9 底噪光斑：保留观感，改绘制方式

**决策**

`.graph-tide` **保留**（G-4 原话：「其实那个还挺好看的」），但**绘制方式**从
「每帧 600 个 alpha 混合光斑」改为「**预渲染 + 每帧一次 blit**」：

1. **预渲染**：把 5 条色带 + 尘埃点 + 短线段（`workbench.js:1482-1488`、`:1589-1622`）
   在**半分辨率**离屏画布上渲染一次（尺寸随 `graphTideResize()`，`:1501-1513`）。
   〔实证〕底噪是极低 alpha（0.018–0.13）的纹理，半分辨率放大后肉眼无差。
2. **每帧**：一次 `drawImage`（带缓慢的亚像素漂移，保留现状的「活纸纹」感）
   + **节点挖洞**用 `destination-out` 在**可见节点位置**画径向渐变
   （≤31 次渐变，而不是 600 个点 × 31 个节点的 18,600 次距离计算）。
3. **求解时的 surge**（`graphTideSurge()`，`:1497-1499`）改为对 blit 的整体
   alpha / 缩放施加，而不是重算 600 个点。
4. `prefers-reduced-motion` 下仍只画一帧（现状 `:1634`、`:1639`）—— 保持不变。

**理由**

- 〔实证〕诊断原文：「它是**每帧 600 个 alpha 混合光斑**的开销，
  与『纸纹底噪』这个功能相比代价过高 —— 建议改为**静态预渲染**或降频」。
- 〔实证〕挖洞遮罩（`graphTideNodeMask()`，`:1515-1530`）是底噪与数据的**唯一耦合**；
  把它从「每点计算」改成「每节点一次渐变」是等价且廉价的。
- G-4 要的是**观感**，不是**实现**；预渲染保留观感。

**否掉的备选**

- **删掉底噪**：G-4 明确保留。
- **原样保留每帧重绘**：把 18,600 次/帧的距离计算留着，正是诊断点名要治的病。
- **完全静态（不漂移）**：丢掉「活纸纹」的手感；折中方案是「预渲染 + 亚像素漂移」。

**代价**

- 底噪的**像素**与现状不再逐点相同（半分辨率 + 漂移方式不同）
  ⇒ 像素比对协议必须把 tide 画布列为**已知差异区**（D-12）。
- 挖洞的边缘在 ½ 分辨率下会略有柔化 —— 与「极淡底噪」的定位相符。

### D-11 相机与 Fit

**决策**

**D-11.1 首次 Fit 之前：把初始相机改成「按 Fit 口径算出来的相机」**

- 现状：初始相机是硬编码 `{ scale: .7, panX: 52, panY: -18 }`（`workbench.js:703`），
  而种子簇摆在舞台中心（`graph-physics-core.js:1528-1530`）
  ⇒ 〔实证〕初始相机下 **31 个节点中 23 个落在画布外**，露出的 8 个挤在右下角
  （基线截图 `tmp/frontend-audit/10-baseline-graph.png` 正是这一帧），
  且这个状态要持续到求解收敛（数十秒级）。
- 决策：**初始相机用 `graphFit()` 的同一套公式，对「当前已有的节点范围」计算一次**
  （节点一创建完就调），而不是等 settle。这样**第一帧就是整图可见**；
  收敛后现有的那一次 auto-fit（`workbench.js:1406-1410`）照旧发生并微调相机。
- 否掉的备选：把 `scale` 从 0.7 改成别的常数 —— 只挪动问题；
  保持 0.7 不动 —— 23/31 在画布外的问题原样保留。

**D-11.2 Fit 改用「节点圆盘包围盒」，不再用「含标签留白的 footprint 包围盒」**

- 现状：`graphFit()`（`workbench.js:1203-1229`）用 `GraphPhysics.footprint(node)`
  （`graph-physics-core.js:93-101`）算包围盒，其中 `half = max(size/2 + 13, labelWidth/2)`
  ⇒ 〔实证〕包围盒 1142×1147 世界 px，而**节点圆心**只占 890×919。
  标签留白让整图缩到 0.37。
- 决策：Fit 的包围盒改为**节点圆盘**（`node.size` 的投影）**+ 固定屏幕边距**，
  **不再包含标签留白**。理由：标签现在有独立的屏幕空间去冲突 pass（D-6），
  它的宽度不该再决定整图的缩放。
  ⇒ 〔实证/估算〕包围盒从 1142×1147 缩到 ~890×919 ⇒ 860×460 画布下
  scale 从 0.35（已计入 D-3 的世界尺寸变化）升到约 **0.41–0.47**，
  节点之间的**间距**整体放大约 20–35%。
  （节点的**大小**与缩放无关，见 D-1；这条改动放开的是间距，不是直径。）
- 代价：标签可能落到画布边缘之外 ⇒ 去冲突 pass 需要把「标签矩形超出画布」
  也算作一次冲突（先藏）。

**D-11.3 「中栏宽度一变整图缩放就变」—— 这是 fit-to-viewport 的固有性质，不是缺陷**

- 〔实证〕`graphFit()` 用 `graphCanvas.clientWidth/clientHeight`（`:1223-1224`）
  算缩放，中栏宽度变 ⇒ 画布变 ⇒ 整图缩放变（graph-isolation.md 的 F-22）。
  这**是**「适应画布」的语义，**不是**要修的 bug。
- 真正要修的是「缩放还被**标签文字长度**牵着走」（D-11.2 已解开）。
- 附带影响：整图缩放变化会让 WebGL 的 `width / scale` 补偿（`graph-renderer.js:282`）
  与 `graphTideResize()`（`workbench.js:1501`）一起变 —— 两者都是按当前 scale/dpr
  重算的，**无状态残留** ⇒ 安全。

**D-11.4 缩放条的行为变了（要交代）**

- 现状：`+` 每次 +0.09、上限 1.6（`workbench.js:1885`）；滚轮缩放的下限是 0.38、步长 ×0.92/×1.08（`:1762`）。
- 新语义：**放大不再让节点变大**（节点尺寸是屏幕 px，与缩放无关）⇒
  缩放的用途变成**拉开间距 / 看整体**，而「看清细节」改由**悬停与看板**承担。
  这也正好是 D-1 那个「拥挤时放大即分离」的对偶。
- 决策：**保留现有的量纲与上限**（0.09/档、1.6 上限），只把工具条的
  `title` 文案改成反映新语义（「拉开间距」），并在 PRODUCT-MANUAL 里同步。
  不改缩放档位（会改变 `workbench-ui` 的交互契约，且没有必要）。

**否掉的备选**

- **收敛过程中持续 Fit**：相机抖动，且违反「相机变化不 reheat」（`workbench.js:1107-1108`）。
- **把 Fit 的输入换成「标签实际测量宽度」**：那会让缩放依赖字体度量与换行，
  比现在更脆。

**代价**

- 首帧的相机从「固定 0.7」变成「按当前节点范围算出来」⇒ 第一次进入图谱页时
  相机值与现状不同（这正是要修的）。已有的 `localStorage` 布局种子
  （`graph-physics.js:43-48` 的 `lk_graph_layout_v1_<workspace>`）**不受影响**：
  种子里存的是节点 id 与坐标，节点数与坐标语义都没变（见 Migration Plan）。

### D-12 夜纸适配，以及「亮色逐像素不变」的结论

**D-12.1 图谱 token 改名 + 夜纸值集**

- 〔实证〕图谱的 12 个裸名 token 声明在 `:root`（`workbench.css:1505-1518`），
  且**在图谱区段外引用 0 次**（本文件 Context 第 5 条的实测命令）。
  ⇒ 改名是**机械且可验证**的：把 `--paper / --ink / --hair / --blue / --blueSoft /
  --yellow / --yellowSoft / --red / --redSoft / --green / --graphite / --shadow`
  改为 `--graph-paper / --graph-ink / …`（同区段内替换），并在
  `.openspec` 的断言里保留「区段外引用 0 次」这一性质。
  **动机**：graph-isolation.md 的 F-1 / F-2 指出，裸名 `--ink / --paper / --shadow`
  与任何新 token 层同名 ⇒ 静默取到图谱的值。本改名**一次性消除**该风险。
  〔实证〕`--green` / `--graphite` 无引用（D-10 第 7 项）⇒ 随改名一并删除。
- 夜纸值集：新增 `html[data-theme="night"]` 块，重新声明图谱的 token。
  〔实证〕`html[data-theme="night"]` 的特异性 (0,1,1) **高于** `:root` (0,1,0)，
  因此它会压过图谱的 `:root`（F-15 记录的机制事实）。
  由于图谱 token 已改名且区段外零引用 ⇒ **不会外泄**到别的页面。
- 夜纸取值：纸面 `#1c1a16`（全站夜纸基色，由 `workbench-visual-language-v2` 定，
  本变更不另立）、墨 `#efe8db`；节点/状态/量值的夜纸值见 **D-4 的表**。
- 〔依据〕A-7 / A-8：夜纸下知识图谱跟随夜纸，图谱的纸面、墨线、节点与关系线
  按夜纸值集重新着色；**结构、布局、物理、交互、指标投影语义一律不变**。

**D-12.2 G-18 与 G-19 的张力：显式处理**

- G-18：「关系线端点接到外环边缘……但**关系线本身的线型、粗细、颜色不改**」。
- G-19：「夜纸下的**分类色**：同一色相、提亮降饱和」。
- 冲突：亮纸下 `legacy` 关系线是 `#bbb4a9`（对纸 2.02:1）；
  夜纸下若照搬，它对 `#1c1a16` 只有 1.95:1 ⇒ 几乎不可见。
- **结论（冲突的显式裁决）**：
  **G-18 的「颜色不改」限定在亮色主题** —— 它约束的是「节点改形不得顺手重画关系线」；
  **夜纸的值集属于主题适配**（A-7 / A-8 明确把夜纸适配划给本变更，G-19 规定分类色的夜纸处理）。
  ⇒ **亮色主题下 5 条关系线的颜色值逐字节不变**；
  **夜纸主题下 5 条关系线取同色相的夜纸值**（D-4 的表已列出），
  图例同步跟随。
  这条冲突**显式登记**在 `docs/PENDING-DEFINITIONS.md` 之外 —— 需在
  `workbench-ui` 的 delta 里写明「关系线的亮色取值不变、夜纸取值是主题适配」。

**D-12.3 「亮色逐像素不变」的结论：重新定义基线**

- G-5（`workbench-visual-language-v2/acceptance.md:22`）的原文是
  「**图谱页未被本变更触碰**（否定式断言）… 差异像素数 = 0。
  图谱**不在本变更的验收范围内**（`decisions.md` A-8：图谱的夜纸适配与节点视觉重设计
  归独立 change `graph-node-visual-language`）；零差异不是一条待达成的门禁，
  而是『本变更根本没碰它』的证明」。
  ⇒ 〔实证〕它约束的是**那个变更**（证明新的 token 层没有改变图谱页的观感），
  **它不是本变更的约束** —— 本变更存在的目的就是改变图谱节点的观感。
  换句话说：**「亮色逐像素不变」这条要求，在本变更里根本不存在**；
  真正要守住的是它背后的那个意图 —— **图谱的 token 层不得被全站 token 层牵连**
  （即 graph-isolation.md 的 L1 零全局依赖，见下）。
- **结论：重新定义基线。**
  - 旧基线（`tmp/frontend-audit/10-baseline-graph.png`）**退役**为「改造前参考」，
    不再作为「必须逐像素一致」的判定基准。
  - **新基线 = 本变更落地后的截图**，且比对协议的**目的**从
    「前后必须相同」改成 **「差异必须被限制在声明的区域内」**：
    差异像素集合 ⊆ （节点区 ∪ 标签区 ∪ 图例区 ∪ 底噪画布区）。
  - 协议本身**沿用** graph-isolation.md §6 的全部冻结手段与状态矩阵：
    三处不可比源（tide 的时间驱动 / Worker 迭代 / `localStorage` 种子）的冻结、
    S-G1…S-G7 状态矩阵、R-2（画布区域）口径。
  - **仍然成立的那条硬约束**：图谱的**结构**不得变 ——
    节点数、节点位置、边集合、边的几何、相机、交互结果**必须与改造前一致**；
    截图差异只能来自节点/标签/图例的**画法**。
    这就是「结构不变」的可验证形式。
  - **R-1 / R-2 / R-3 的口径争议**（graph-isolation.md §6.7「需所有者裁决」）
    **在本变更里失效**：那个争议是「token 层改造是否该动图谱页的外壳」，
    而本变更只管图谱本身；外壳（左栏 / 顶栏 / 右栏）的验收仍归
    `workbench-visual-language-v2`。
- **仍须遵守的移交约束**（graph-isolation.md §4 / §5）：
  图谱区段**不得**引用 `var(--lk-*)` / `var(--dsw-*)`（C-8 的「L1 零全局依赖」
  这条可断言性质必须继续成立）⇒ 本变更的图谱 CSS **继续自足**，
  新的夜纸块也必须限定在图谱作用域内。

**代价**

- 旧的像素基线截图不再有判定效力 ⇒ 需要为新基线补一组截图与状态矩阵。
- 「差异 ⊆ 声明区域」需要一张**区域遮罩**（节点/标签/图例的包围盒并集）——
  可由 DOM 的 `getBoundingClientRect` 在截图时导出，作为比对脚本的输入。

### D-14 契约协调与并行变更

**决策**

1. **落地顺序**：`workbench-visual-language-v2` **先**，本变更**后**。
   理由：本变更的夜纸值集以它的夜纸基色（`#1c1a16`）为准；
   且它的 `workbench-ui` delta 改写了 `Soft Mondrian visual foundation`
   （`specs/workbench-ui/spec.md:317`），本变更要在其之上追加「图谱例外」段落。
2. **同一 Requirement 被两个变更改写**：
   `Soft Mondrian visual foundation` 与 `Redundant state cues`
   ⇒ **显式登记为协调项**（AGENTS.md 的 contract reconciliation）。
   处理：先合入 v2 的 delta，本变更的 delta 以**完整的最终块**覆盖
   （MODIFIED 必须复制既有需求的整块，见 SYNTH 的 OpenSpec 格式要求），
   并**退役** v2 里的场景「The knowledge graph page is unchanged」
   （`specs/workbench-ui/spec.md:367-371`）—— 它在本变更落地后不再成立。
3. **既有契约漂移的显式登记**（本变更触及、但不改变其行为）：
   - `.meta` 行的存在与 `workbench-ui:245-248` 的「label/meta LOD」措辞
     ⇒ delta 里去掉 `meta`。
   - 「Node labels SHALL always display their complete text」与实现的简称截断
     ⇒ delta 里改写成与实现一致的表述（D-6）。
   - 图例「相关」色与 WebGL 实况不一致 ⇒ 本变更修好（不是漂移，是缺陷）。
4. **术语**：本设计**不引入新的正式设计名词**；
   「同心圆 / 内核 / 外环 / 色键 / 下限」是几何与实现描述词，不是契约名词。
   〔纪律〕若 specs 阶段要把「投影色键」立为正式名词，
   必须先在 `docs/GLOSSARY.md` 建条目；未定义的概念只能进
   `docs/PENDING-DEFINITIONS.md`，**不得**以挂名状态混进正式文档。

**代价**

- 两个变更的 `workbench-ui` delta 需要人工合并（同一 Requirement 被改两次）——
  这是并行的必然代价，显式登记比静默覆盖好。

## Risks / Trade-offs

| # | 风险 | 缓解 |
|---|---|---|
| R-1 | **屏幕像素半径 20–44 在窄中栏下会挤**：〔实证/估算〕860×460 画布、Fit 后节点簇约 410×424 屏幕 px（面积 ~174,000 px²），31 枚半径 20–44 的圆合计约 82,000 px² ⇒ **覆盖率约 47%**，相邻圆盘会压盖；703×372 画布下覆盖率升到 ~75% | 四道缓解：① **内核是淡填充、外环是描边** —— 两枚淡内核交叠不刺眼，压盖主要发生在描边上，可读；② **数字与标签画在所有圆盘之上**（z 序），信息永不被遮；③ **标签让位**（D-6）消掉标签碰撞；④ **放大即分离** —— 节点尺寸与缩放无关，放大只拉开间距，拥挤时放大即可。**兜底**：若走查判定过挤，唯一可调的是 G-17 的下限 20（一个常数），改动需同步改 spec（spec 里写的是「20 到 44 屏幕像素」，属规格数值不是实现细节） |
| R-2 | **小画布（≤411×230）上圆盘几乎必然重叠**（覆盖率 >200%） | 该尺寸本就是极端情况；画布上的对策是**放大 + 平移**（节点尺寸不随缩放变小，所以放大永远是有效的分离手段）；产品侧的长期对策是把图谱页在中栏里做成可全屏，但不是本变更的范围 |
| R-3 | **标签的世界占位与模型估算脱节**（低缩放下约 3 倍） | 由 D-6 的屏幕空间去冲突兜底；**不改** `labelWidth()`（那会改布局物理） |
| R-4 | **D-1 与 D-11.2 的相互作用**：改 Fit 的输入会改 scale ⇒ 改 D-1 的下限命中范围 | 两者都改完后**重新复算**那张表（实现时必做的一次离线复算），并把结果写进 `docs/audits/` |
| R-5 | **底噪预渲染改变像素**（D-9） | 像素协议把 tide 画布列为已知差异区（D-12.3） |
| R-6 | **端点与圆盘错位**（D-7 的两处公式若漂移） | 两端共用 `nodeScreenRadius()` 一个函数；交付前加一条断言 |
| R-7 | **夜纸的关系线可见性**（`legacy` 在夜纸上 1.95:1） | D-12.2 已裁决：夜纸取同色相新值；`legacy` 仍是全图最淡的一档（与亮纸的 2.02:1 对称） |
| R-8 | **两个变更改同一 Requirement** | D-14 的顺序 + 显式登记 |
| R-9 | **实现时误改图谱区段外的全局 token 落点**（graph-isolation.md §4.9 的 B-1…B-6） | 沿用 graph-isolation.md §5.5 的自检脚本（只读）作为交付前检查 |
| R-10 | **术语纪律**：specs 阶段可能临时造词 | D-14 第 4 条：正式名词先入 `docs/GLOSSARY.md`，否则进 `docs/PENDING-DEFINITIONS.md` |

**Trade-offs（明确的取舍，不是缺陷）**

- **世界层保精度 vs 屏幕层保可读**：D-1 选了「逻辑层不动、绘制层屏幕化」。
  代价是标签的世界占位与模型脱节（R-3），换来的是物理零改动。
- **保标签完整 vs 保画面干净**：D-6 选了「不截断 + 重叠让位」。
  代价是需要一次批量测量，收益是既满足 `workbench-ui:471-473` 的「不截断」，
  又满足 G-5 的「常态可见但降对比度」。
- **保底噪 vs 保帧率**：D-9 选了「保观感、砍实现成本」。
- **保亮色的关系线逐值不变 vs 夜纸的可读性**：D-12.2 选了「亮色不变、夜纸换值」，
  代价是同一个色相有两套值（与 A-7 的「夜纸是第二套值」一致）。

## Migration Plan

1. **无数据迁移**：无 schema 变更、无 API 变更、无 CLI 变更、无持久化字段变更。
2. **部署顺序**：
   ① `workbench-visual-language-v2`（token 层 + 夜纸基色）先合入；
   ② 本变更再合入（`workbench-ui` delta 以 v2 之后的整块为准）。
3. **本地布局种子的兼容**：`localStorage` 的 `lk_graph_layout_v1_<workspace>`
   存的是节点 id 集合与坐标；本变更**不改变节点数、不改变坐标语义**
   ⇒ 旧种子继续有效，**不需要清缓存**。（若实现中发现节点数会变，
   则必须改种子的版本判定 —— `workbench-ui:235-238` 已给出「版本不符即忽略」的路径。）
4. **回滚**：纯前端静态资源改动 ⇒ 回滚 CSS / JS 提交即可，**无数据需要回滚**。
5. **静态资源缓存**：`app.py:214-232` 的 `_send_static` **不发** `Cache-Control` /
   `ETag` ⇒ 浏览器启发式缓存可能遮蔽新样式（graph-isolation.md F-18）。
   ⇒ 验证与截图前一律**硬刷新**；本次**不**顺手加长缓存（避免把缓存问题带进变更）。
6. **验证节奏**（每个可验证单元都跑）：
   ```bash
   python -m pytest tests -q
   python -m compileall -q lessonkit.py workbench pipeline pool tests
   openspec validate --specs --strict
   ```
   外加图谱专项：
   - graph-isolation.md §5.5 的只读自检脚本（区段零全局依赖 / 12 个裸名 /
     Georgia 5 处行号不变 / 关键值未改 / 128px 预留仍在 / reduced-motion 兜底仍在 /
     `#middle-page` 无动画 / 图谱 JS 未误改）；
   - D-10 的「死规则命中 0 次」断言；
   - D-12.3 的像素协议（差异 ⊆ 声明区域 + 结构不变断言）。
7. **离线复算**：用 `tmp/frontend-audit/GRAPH-NODE-PIPELINE.md` §12 的复算方法，
   在实现后重跑一次，产出新的「屏幕占用 / 标签可见数 / 直径」表，
   并与 D-1 的表比对（偏差 >10% 需回看设计）。

## Open Questions

只放**可延后**、且**不改变规格 / 方案 / 任务拆分**的问题：

1. **底噪预渲染的分辨率倍率**：本设计取 ½。若 ½ 在低端机上仍不够，
   可降到 ⅓ —— 只影响实现参数，不影响观感判定与规格。
2. **标签让位的「让位对象」权重**：本设计用「半径 → 重要度 → id」。
   若实际使用中觉得「大节点更该保留标签」，可调换前两项 —— 属实现参数。
3. **量值分档的 4 档阈值**（`.25 / .5 / .75`）：需用真实分布校准；
   若某一档在某章空置，可改用分位数分档 —— 不改「单色阶」这一规格。
4. **夜纸下 `.graph-tide` 的透明度**：夜纸的底噪需要单独压暗（亮纸下是
   `opacity: .92` + `multiply`）。取值属实现参数，但**必须在夜纸值集里显式给出**
   （不能沿用亮纸的 multiply 结果）—— 实施时定稿即可。
