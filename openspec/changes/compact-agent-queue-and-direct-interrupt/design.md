# Design

## 决定与边界

复用 GLOSSARY 已定义的“待发消息”“中断后发送”“本地发送箱”。截图中的“栈”是布局描述，不是新的调度实体或 LIFO 语义。选择一个紧凑的待发列表，保留默认 FIFO 和既有串行执行，比另建前端队列或把中断消息插入优先队列更直接。

对比方案：只缩小现有卡片无法解决中断/恢复状态混入队列；新建前端队列会产生第二份执行事实。采用既有 Bridge 状态驱动的单一列表，中断由独立的停止后交接路径执行。

## 输入区

从上到下为：待发列表（非空时）、本次发送/恢复的短状态（存在时）、输入框和发送控件。历史区继续承担已开始或已终结的轮次与真实失败记录，不重复复制同一条待发消息。

列表每行显示文字预览，操作依次为拖动手柄、“立即发送”、编辑、删除。文字可展开或进入编辑读取完整内容；默认单行截断。最多显示四行的高度，更多项在列表内滚动，不挤掉输入框；窄屏可换行排列操作但每项不重复状态说明。暂停状态/继续按钮全列表只有一份。拖动提供键盘上移/下移等价操作，图标有可读名称。

编辑在行内完成，确认后才写入；取消编辑不改消息。删除沿用既有取消记录语义。刷新、换页、切换对话后从服务端恢复确认顺序，异步回调不得修改另一对话。

## 排队与重排

只有被服务端接受为 `queued` 的消息出现在列表。默认按提交顺序添加至尾部；服务端显式队列顺序是调度和 UI 的同一事实。重排与 dispatch 使用既有同一对话 ownership lock，不能让 UI 顺序与实际执行顺序分叉。

拟在 `conversation.json` 增量保存 `queue_order`（turn ID 数组），只包含 `queued` 项。旧工件缺字段时按现有数字 turn ID 顺序读取；首次成功队列变更才保存显式顺序，不批量迁移。`waiting_for_stop` 不进入 `queue_order`。删除、dispatch 和提升为立即发送时更新同一顺序；service recovery 保留顺序并暂停，不自动执行。

拟增 `POST .../queue/reorder`，请求 `{expected_order, turn_ids}`：前者为客户端读取的完整待发顺序，后者必须是其全排列。锁内比对当前完整顺序和排队资格，任何新增、删除、dispatch 或另一端重排造成的不一致返回 409 且零修改；成功返回确认顺序。顺序不改变消息身份、文字、上下文或不可变的原提交字段。已有消息 edit/remove 的 `expected_revision` 契约保持。

## 中断后发送

新消息仍使用既有 turn 提交和 `queue_action=interrupt`，但不能落入普通队列或由 `/queue/continue` 驱动。Bridge 在锁内持久接收并捕获当前正在执行的轮次，立即请求停止；等到该 worker 终态与释放后直接交接。停止中仅显示单条“正在停止当前回复，随后发送…”状态。无法确认停止时如实等待，不超时并发启动，不自动改成排队。

没有当前 worker 时直接执行；旧队列暂停不阻挡一条明确的中断发送（待审批除外）。如果原轮次正常结束与停止请求竞态，仍在释放后直接运行指定消息。原任务完成的效果保留，不自动回滚/续跑。

已有队列 B/C 时发送中断消息 D，D 不加入 B/C，不显示队列位置；D 结束后 B/C 仍暂停。没有 B/C 时不创建队列 UI。等待停止过程中第二条不同的中断发送返回 409，保留第二条草稿，不替换已接受消息，也不建立中断消息队列。

## 待发消息的“立即发送”

拟增 `POST .../turns/{turn_id}/interrupt`，请求 `{expected_revision}`。这是对既有已接收待发消息的明确路由变更，不是重新提交相同 `submission_id`，后者继续只核对原接收结果。

锁内核验该项仍为 queued、revision 匹配、没有另一条停止交接且不存在待审批，再从普通队列移除并进入上述路径。保留原 turn/submission identity、当前已编辑文字和原上下文；其他项顺序不变、保持暂停。没有正在运行的 provider 时直接启动该项。与 dispatch 竞态失败时 409 且不取消其他轮次、不复制任务。重复请求对同一已提升 turn 返回同一结果，不重复停止新轮次或执行消息。

## 恢复与审批

`queued`、`waiting_for_stop`、状态未知的本地发送箱记录、已失败历史是四种不同事实。已接收结果按身份对账后从本地发送箱去重；排队列表只出现第一种。未知状态保留原 submission identity 核对，拒绝消息保留原文，失败历史提供原有显式重试；这些都不自动变成待发消息。输入区只出现一份恢复摘要和数量，展开后逐条处理，失败历史保留内联操作，不在 composer 上方重复铺满大卡片。不覆盖较新的输入草稿，不自动核对后重放操作。

待 Paper 审批时，显式 queue 仍加入暂停队列；interrupt 或行内立即发送被拒绝，保留输入/原队列项并提示先处理审批，不能默默改成 queue。这是对两个 capability 中“所有新消息排队”既有条款的显式修改，不改变批准/取消的写入边界。审批解除后旧队列仍须明确继续。

| `FILE_CONTRACT.md` | `queue_order`、两个操作的请求/响应/409/幂等边界、旧工件默认顺序；区分 queued 与 waiting_for_stop |

| `docs/ARCHITECTURE.md` | Shell 渲染和薄路由，Bridge 唯一负责对话顺序/停止交接；Domain/Data 不新增调度职责 |
| `docs/PRODUCT-MANUAL.md` | 输入区列表与四个操作、直接中断、恢复摘要及审批拒绝说明 |

当前事实仍由当前职责文档约束；此设计只在获准实施后改变它们。无真实会话批量迁移、无真实池写入。
