## Context

The user message currently survives only as an optimistic DOM bubble until a successful exchange is appended to `transcript.jsonl`. Failed turns do not produce that exchange; a fresh history read therefore loses their user text. Startup also recreates the list view on full-document navigation. The desktop HTML demonstrates behavior, not a visual or layout contract. See the dated investigation for code evidence.

## Goals / Non-Goals

**Goals:** durable visible messages regardless of execution result; a persistent right rail within one workspace; a single running turn plus controlled pending messages; truthful tool/failure/approval UI.

**Non-Goals:** concurrent provider tasks in one conversation, a new task scheduler/service, automatic resurrection of stopped work, aesthetic reproduction, a design-control panel, unrestricted replay of arbitrary tool commands or exposing private reasoning.

## Decisions

1. **One message identity before the network boundary.** Reuse the existing client operation-identity convention or a platform-generated non-hash request ID; retain it with outgoing text and the submitted context locally before clearing the composer. Server acceptance persists message text, identity, order and context before returning success or starting a provider. Repeating the same identity/payload returns the same accepted message/turn without dispatching twice; changed payload under the same identity is rejected. A locally failed/unknown send remains visible and recoverable across refresh, distinct from canonical accepted history. Do not overwrite a newer composer draft when recovering old text.
2. **Messages are not successful exchanges.** Extend the existing conversation artifacts so reads include accepted queued/running/failed/cancelled messages, even if no assistant answer exists. Associate assistant activity/output/failure with the originating message/turn. Preserve partial public output where available, with terminal status. Read legacy successful transcript pairs without duplicating their user messages. Never synthesize an assistant answer for failure or silently drop a user's message because its provider failed.
3. **Serialize dispatch per conversation.** Reuse the existing process/thread and `_LOCK` ownership, making one canonical pending order and one active turn. Queue acceptance is not a running provider. FIFO entries retain the context captured at submission, even if the middle page changes later. Support inspecting/editing/removing messages that have not begun; editing updates their expected identity/revision without duplicating them. User acceptance survives page closure/refresh; while the local service is running, accepted queue work follows the selected queue policy independently of the tab. Service recovery marks an unowned running turn interrupted and pauses its retained queue; it does not silently start provider work after restart.
4. **Explicit interrupt-and-send.** For running A, queued B/C and priority D: persist D and the interruption intent; request existing cancellation; wait for authoritative terminal acknowledgement, then run D once. If cancellation cannot be confirmed, do not launch D concurrently; keep it visible as waiting for stop confirmation. Preserve A's already completed effects, never auto-rollback or resume it. Keep B/C paused after D, even when D succeeds; the user explicitly resumes/edits/removes them. An ordinary task failure or unexpected interruption likewise pauses the queue. A progress-read network error alone is unknown status, not a terminal failure and not permission to dispatch another task.
5. **Settings use the existing workspace preference convention.** Default running-message behavior is queue; the user can change the default to interrupt-and-send in settings, while both explicit actions remain available. Persist settings with the existing workspace/browser settings mechanism and label the effect clearly; changing a setting affects subsequent submissions only, never a running task or already accepted message's order.
6. **Keep the rail mounted.** Introduce a workspace navigation boundary which updates the middle content and its owned lifecycle while preserving the existing right-rail controller/DOM. Support internal practice/Paper/KP/graph/records navigation, query-state changes and back/forward; a canonical deep link or full refresh remains supported. Do not recreate the rail, rerender its history, lose focus/draft/scroll, reset polls or hide it behind the list for middle-only navigation. Update page-context chips for the new middle page; capture new-message context at submission. Dispose old middle-view listeners/graph workers before initializing the new middle view. Reuse server-rendered middle markup and existing page modules rather than introducing a frontend framework or iframe. Workspace changes keep their existing conversation/data isolation.
7. **Clear recovery semantics.** A definitely unaccepted message can be edited and resubmitted. Unknown acceptance first reconciles by the same operation identity; it must not manufacture a second request. Retrying an accepted failed turn is an explicit new attempt linked to its original message, not deletion/replacement of history or automatic replay of successful writes. A Tool Call Card shows semantic label/state/outcome and actual known impact, with raw diagnostics folded/redacted. Show a recovery button only if the backend supports its exact action. Without a safe per-operation retry, offer an explicit new Agent instruction or read-only inspection rather than a fake 'Retry failed' button.
8. **Reuse governed approvals.** Existing rollback approval stays intact. Paper structure updates requiring progress reset use the impact preview/confirmation defined by the Paper change. Do not add a generic approval gate to every normal tool. Scope callbacks by workspace/conversation/message and operation revision; cancellation or switching conversation invalidates stale approvals.
9. **Activity progress surfaces have a separate owner.** The Activity Float/Bottom Dock selection, collapse/reopen behavior, idle cleanup, and Dock retirement are specified only by `use-collapsible-agent-activity-float`.

## Compatibility and rollout

Preserve provider/model ownership, native-session continuation and current working-directory contracts. Same-conversation simultaneous turns remain forbidden. Existing exported artifacts and successful transcripts remain readable. Inventory supported provider cancellation behavior; no provider may advertise resumable suspension merely because it supports abort. Bridge must persist message acceptance before any provider launch, including launch failure. UI clients must use idempotent acceptance/reconciliation before enabling automatic queue dispatch.

Document new artifacts/status fields in FILE_CONTRACT and any affected DATA_MODEL ownership; reconcile live specs and Action Graph in the implementation PR. No real course conversations or provider processes are mutated by specification preparation.

## Acceptance

Use fake providers and isolated registries, including rejected POST, lost acceptance response, provider startup/runtime failure, cancel timeout, polling loss, service restart, double-click/retry and legacy transcript reads. Browser checks must assert actual rail DOM/controller identity and input/scroll/poll retention, not merely restored conversation ID. Trace A/B/C/D ordering and prove at most one provider worker per conversation. Then independently run required repository gates and isolated browser acceptance.
