# Design — Contract parity and a declarable practice mode

## What the Agent was actually reading

The live service started at 17:24 and the multi-chapter code was written at
17:55/18:29, so on 2026-09-25 the Agent still received the pre-change contract
(`条数没有上限；一个清单就是一个批次`) and the pre-change extraction (first
block wins). That explains the report but not the whole story: with the current
tree in front of it, three statements still lead to the same conclusion.

| Statement the Agent sees | What the code does | Fix |
|---|---|---|
| 「小清单也可以在区块里内联 manifest」 | an inline `{"type": "content-bundle", …}` is refused (`manifest kind must be …`) because only `kind` is accepted | accept `type` as an alias of `kind`; show the shape in the prompt |
| 「顶层也没写就用当前章」 | `_gate_content_bundle(conn, manifest, course, chapter)` — no caller passes `chapter`, so a chapter-less item is refused `chapter is required` | keep the refusal (a multi-chapter manifest must never be silently mislabeled into the lens chapter), delete the dead argument, and say so in the prompt with an actionable reason |
| 「并**按章各记一个批次**」 + 「整批预检…整批零写入」 | one batch per chapter is right; the prevalidation, backup, and transaction cover the whole manifest | state both halves in one place so 批次 ≠ 提交范围 |

## Why a keyless objective item

The learner's bank is mostly 判断题/单选题 and the exports lost the answers.
Today the only route into 小测/判断 is a fully-formed micro item, so a keyless
objective question has to enter as a plain problem — and a plain problem is
**exam-only by contract** (`pull._eligible_for_mode`). The result is that the
判断 and 小测 shells are empty for both real courses.

Decision (learner's): an objective item may enter **without** a key.

1. `answer_key` absent or `null` marks the item keyless. `yes_no` keeps its
   implied 是/否 options; the choice types still need 2–6 options, because
   without options the item cannot be presented at all — such a question belongs
   in the exam mode (or its options go into the stem).
2. `error_reason` stays mandatory **when a key is present** (it explains a wrong
   answer) and becomes optional when the key is absent.
3. The mode marking does not change: `quiz_type` decides, exactly as today
   (`yes_no` → `["yes_no"]`, `single_choice`/`multiple_choice` → `["micro"]`).
   "Choosing 综合题/判断/小测 at import" therefore means: no `quiz_type` (综合题),
   or `quiz_type` + `options` (+ `answer_key` when known).
4. Keyless is **visible**, not silent: the batch result carries a keyless count,
   the ingest-batch registry keeps it with the other counts, and the next-turn
   context repeats it. An Agent that forgets a key it had is corrected on the
   next turn instead of quietly producing ungradable items.
5. A key can be filled in later. `answer_key` joins the editable problem fields
   (`lesson-kit data update problem <id> --input '{"answer_key": "是"}'`),
   validated against that item's own quiz type with the same rule as ingestion;
   an empty value clears it back to keyless. It is deliberately **not** in the
   difficulty-reset group, so filling keys never wipes a rating.

## Ungraded rendering

`gradeMicroQuiz` today compares the submission to `quiz.answer_key` whatever it
is: with a null key every answer is marked wrong (`submitted === null` is false)
and 查看解析 prints an empty 答案. The fix is small and local: return `null`
(the existing "not graded" value that ordinary problems already produce) when the
item's type needs a key and none is stored. Everything downstream already
handles it — `verdictLine` renders nothing, no option is highlighted, the answer
text and choices are still recorded, and the rating flow (the only writer of
learning state on this page) is untouched. The card adds one honest line
naming the missing key, and 查看解析 shows 未录入答案键 instead of an empty
string.

## Contract parity details

- Inline blocks: `{"kind": "content-bundle", …}` stays the recommended shape;
  `{"type": "content-bundle", …}` is accepted and normalized. A block that
  carries neither, or a wrong `kind`, keeps today's explicit refusal.
- Chapter rule: item `chapter` → bundle `chapter` → refused, naming the item.
  The refusal text adds that the workspace chapter is not used, so the Agent gets
  the reason on the first attempt instead of inventing a one-chapter-batch rule.
- Continuation: after a successful apply, the next-turn context gains one
  sentence — if the learner asked for several chapters and only some arrived,
  continue with the rest instead of asking for another 「继续」. No automatic
  turn is ever generated by the workbench.
- Version line: the contract block opens with its version and a precedence note
  (「以本条为准」), because a resumed provider session still carries earlier
  contract text in its own context.
- A plain problem that declares a micro/yes-no `practice_modes` without a
  `quiz_type` is refused with the exact fix instead of being silently written as
  exam-only.

## Consequences and non-goals

- Existing rows are untouched: no in-place conversion of `-prob-NNN` rows into
  micro quizzes (the readable id identity would change). The learner re-imports
  both courses after this change; that is a deliberate, backed-up operation they
  drive.
- A keyless 判断题/单选题 is practised without a verdict and relies on the 1–5
  self-rating. That is the honest consequence of a lost answer key, and the
  alternative — guessing a key — would fabricate learning signal.
- Still out of scope: automatic continuation, a practice-page editor for keys
  (the Agent and the CLI can fill keys today), and any pool schema change.
