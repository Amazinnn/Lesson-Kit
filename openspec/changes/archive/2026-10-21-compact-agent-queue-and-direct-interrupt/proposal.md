# 紧凑待发列表与直接中断发送

## Why

当前消息区把待发消息、中断等待和本地发送箱恢复提示混在多张大卡片中，反复出现“重试这条消息”“核对发送状态”，占满对话区域。用户无法从界面直接判断哪些消息真的在排队。

所有者明确要求：选择排队时使用输入框上方的紧凑堆叠列表；选择中断后发送时，停止当前回复后直接处理下一条消息，不建立队列。本 change 只提出设计和验收，不实现、不迁移、不操作真实课程数据。

## What Changes

- 排队消息集中显示在输入框正上方的单一列表，一条消息一行，支持拖动排序、编辑、删除及“立即发送”；队列为空时整个列表消失。
- “栈”指视觉堆叠，不引入后进先出：默认提交顺序，自上而下执行；用户显式重排后以确认后的顺序执行。
- 中断后发送独立于队列：绑定并停止当前轮次，确认停止及 worker 释放后直接执行指定消息。等待停止只是本次发送的短暂状态，不是排队项，不要求“继续队列”。
- 列表行的“立即发送”把该条已接收消息从队列取出并交给相同的直接发送路径，保留原身份、当前文字和原上下文，不另造一次提交。
- 已有其他排队消息在中断后保持暂停，不隐式删除或续跑；没有排队消息的对话不会仅因中断操作产生队列。
- 状态未知、拒绝和已失败消息与队列分开处理；保留恢复与防重复能力，取消重复的大块恢复卡片。
- 待 Paper 审批时，中断发送/立即发送被明确拒绝且消息可恢复，不自动降级为排队。显式选择排队仍可加入暂停队列。

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `workbench-ui`: 待发列表布局与操作、独立中断状态、本地发送箱恢复呈现及审批期间发送反馈。
- `ai-teacher-bridge`: 显式队列顺序、原消息立即发送、中断不入队、审批拒绝边界。

## Impact

实现预计涉及 `workbench/server/pages.py`、`static/workbench.js`、`static/agent-ui.css`、薄 API 路由及 `workbench/bridge/conversations.py` 的既有会话编排。复用会话/轮次 JSON、当前 `submission_id`、原上下文、pending 编辑/删除与停止确认机制，不增加 SQLite 表、provider、调度服务或依赖。

职责文档的实施同步清单见 design.md；本次只新增此 change，不把提议写成当前产品事实。

## Non-goals

不重做 Agent 的全部消息历史、工具活动卡、Paper 审批或 provider 协议；不取消未知状态核对，不自动重试失败消息，不允许同一对话并发 provider，不清除旧队列，不修改真实学习数据。
