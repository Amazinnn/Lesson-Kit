## 总的愿望

lesson-kit 已经接近日常可用。后续的重点不是继续堆页面和按钮，而是让它更像一个真正的学习工作台：知识池是事实来源，图谱帮助发现和选择，练习活动负责执行，外部 Agent 负责解释、追问和陪练。

“能用”始终比“理论上优秀”重要。任何新功能都应该先做出一个小而可靠的版本，再根据真实学习中的问题继续改。

## DeepTutor / NotebookLM 参照

- DeepTutor 值得借鉴的重点是教学过程的分层：课程层决定当前方向，会话层决定本轮目标，回合层决定下一步追问或检查。
- NotebookLM 值得借鉴的重点是把材料加工成不同粒度的学习活动，而不是把整份材料原样摊给学生。
- 不直接复制多智能体或产品功能清单。lesson-kit 仍然保持外部 Agent 可替换、确定性学习核心不依赖 AI。

## 更有限的插件化

当前架构已经有 Shell、Domain、Data、Content、Bridge 的边界，但还不是完整的插件生态。

未来可以考虑只为以下能力建立内部注册点：

- `PracticeMode`：试卷、Micro Quiz、Yes/No、记忆卡片等；
- `GraphProjection`：结构视图、薄弱度视图、复习紧迫度视图、题量视图；
- `GraphMetric`：为图谱位置、颜色、大小提供可解释指标；
- `IngestOperation`：OCR 材料整理、结构化、补解、审计、入池；
- `AgentProvider`：Codex、Claude 以及未来其他本地 Agent。

不急于支持第三方动态安装。先让内置能力遵守清晰契约，就能获得大部分模块化收益。SQLite、反馈、调度、正式内容门禁和基础关系模型不应为了“Everything is a plugin”而被拆散。

## 学习型知识图谱

图谱的基本结构不变：知识点是节点，真实关系是边。变化的是观察方式。

可以让同一张图谱按照不同参数产生不同的二维投影：

- 越生疏的知识点越靠近中心，或越醒目；
- 越重要的知识点越靠近中心；
- 到期复习项聚集到某个区域；
- 题目数量决定节点大小；
- 掌握证据和薄弱度决定颜色或透明度；
- 关系强度决定边长、聚拢程度或局部展开程度；
- 未来也可以使用平面直角坐标轴，把两个指标分别映射到 X/Y。

这些形态变化必须来自可追溯的学习证据，不能把内部字段随意包装成“掌握度”。掌握算法可以是实验性的，但不能伪装成精确测量。

可能的视图：

```text
结构视图
薄弱度视图
复习紧迫视图
题量分布视图
```

图谱适合发现和选择，列表仍适合精确搜索、窄屏和无障碍访问。两者不必互相替代。

一个很自然的学习动作是：多选节点 → 形成知识点集合 → 进入限定范围的连续练习。现有 `pull` 已能接收多个 `kp_ids`，因此这条路径的后端基础并不难。

## 练习活动的分化

### 试卷模式

- 使用正式题池中的完整题目；
- 适合证明、推导、建模、综合应用；
- 允许长答案和较深思考；
- 更接近当前已有的练习流程。

### Micro Quiz / 小测模式

> 2026-08-28 已实现：内容契约、`wb ingest recipe micro-quiz` 入池配方与按题型
> 渲染/客观题本地判分见 `openspec/specs/micro-quiz-content/spec.md`；
> AI 生成微题仍是下述后置实验。

- 一张卡只考察一个较小概念；
- 题干短，反馈快；
- 可以使用选择、判断、匹配和简短回答；
- 更像 NotebookLM 的学习卡片，而不是把长题硬截短。

Yes/No 更适合作为 Micro Quiz 的一种回答类型，而不是单独维护一整套会话系统：

```text
micro_quiz
├── yes_no
├── single_choice
├── multiple_choice
├── closest_answer
└── short_answer
```

真正的小测需要新的内容单位：短题干、选项、正确答案、错误原因、来源证据、原子知识点和题型。不能只把现有长题的前几十个字拿来冒充小测。

## 内容摄取的拆解

原先“一次性完成 OCR、清洗、结构化、补解、审计、入池、生成视图”的流程，对于多变的书籍和试题过于僵硬。

更灵活的方向是把它拆成可以单独运行的工作：

```text
原始材料
→ 准备 / 清洗
→ 结构化
→ 补解
→ 独立审计
→ 门禁
→ 显式入池
→ 生成视图
```

OCR 只是可选原材料，不应成为核心依赖。中间产物用明确的 UTF-8 文件交接，默认零写入，只有显式 apply 才进入 SQLite。

## Agent 教学能力

- 普通对话不应该绑死在练习、诊断或讲解某一个活动上；会话可以自由探索。
- Agent 通过 `wb data` 获取权威材料，Lesson Kit 负责数据边界和写入门禁。
- 页面上下文可以提供当前工作区、知识点、题目、练习范围和最近浏览对象；未提交草稿默认不进入长期记录。
- Agent 可以解释、追问、比较、帮助规划，但不应绕过正式内容门禁直接制造可信度不明的正式题。
- 会话记忆、外部 Provider 原生上下文和 Lesson Kit 的显式问答镜像需要继续保持边界。

## 暂时没有答案的问题

- 掌握证据怎样稳定地映射为图谱颜色、大小和位置？
- 两个图谱指标同时变化时，怎样避免视觉上漂亮但学习上误导？
- Micro Quiz 的最小可信内容契约应该是什么？
- 小测生成后的错误选项如何进行来源审计？
- 哪些练习结果可以反过来改变图谱形态，哪些只能作为一次性提示？
- 插件注册点应该在 Python Domain、前端视图，还是两者之间的共享契约？
- 如何保持多种学习模式增长，而不让界面变成“飞机驾驶舱”？

## 当前优先级直觉

如果学期开始前只能做少量事情，优先考虑：

1. 图谱多选知识点并进入现有连续练习；
2. 建立内部 `GraphProjection` / `GraphMetric` 边界；
3. 设计一个来源可审计的最小 Micro Quiz，先只支持 Yes/No；
4. 在真实学习反馈之后，再决定是否扩展插件注册体系。

## 计划与量化进度（2026-08-27 讨论）

这轮讨论进一步确认：下一版打开后的第一要务，是给出一个按顺序排列的短队列，而不是只丢给学生一个孤立动作。队列可以随完成情况、可用时间和临近考试的状态变化，但不应细化成操作手册。

计划分层：课程或考试给出外部约束；学生确认长周期目标；Agent 根据进度提出或调整阶段性建议；系统用真实完成情况重新安排下一段。长周期目标不由 Agent 擅自替代，Agent 负责规划和维护进度。

短目标保持整体性，例如完成一轮章节复习、处理某部分主要内容、完成一次考前检验。可以有数量、覆盖率和截止时间，但不要规定“做几道题后辨析一次、隔几天重测一次”这类过细动作。

学生看到的量化进度暂定只保留：完成度、课程范围覆盖率、距离考试的阶段状态。UI 可以用多阶段进度条和倒计时日程呈现，但它们只是帮助理解进度的组件，不应变成额外的任务管理负担。

必须矫枉过正地避免依赖逐题主观反馈：这类数据天然稀疏、偏斜且不稳定。学生不可能为数万道题逐题反馈；学生指出的某个薄弱点也不能覆盖未指出的盲区，更不能让 Agent 因信息不足而把推荐范围越缩越窄。

暂定原则是“粗粒度目标，适度量化，内部证据辅助但不支配”。细节可以用于校正和发现风险，但不能直接决定学生必须完成的微动作，也不能把一次偶然反馈当成全局结论。

“为什么不两个都显示呢？我觉得练习界面就应该显示这些东西，对吧？练习界面它就应该显示各种计划和目标，这我反正我是这么想的。可以有那种卡片的样式，给穿插从上到下列一大堆，这也没有问题。不过目标之间也会有重复的，对吧？这个可能就需要后续商量一下，这个可以设计一些算法。顺带一提，我个人觉得那个今天要执行的短序列、短队列，其实应该还是比较简单而整体的，不需要加入特别精细的动作，否则也会给学生带来负担，这个我前面已经反复强调过了。”

结构化理解：练习界面同时展示长期计划/目标和今天的短队列，可用纵向卡片呈现；重复目标后续再研究合并算法。短队列保持简单、整体，不拆成过细动作。相关学习模型只作为参考：间隔与检索支持长期保持，自我调节学习强调计划—执行—反思循环，但不应把模型术语直接变成学生任务负担。

“一个比较Experimental的想法就是，可以让学生自己选定学习模型，并由学生选定一些具体的参数。而且还有一个可视化的学习曲线，或者说计划中的学习曲线让学生参考，而且会随着学生选择的参数变化而变化。可以有一些数学图像的设计加进去，当然这都是前端设计的问题了。这个比较experimental，所以以后再慢慢实现也不着急。
你上面这些其实就挺好的，不过也涉及到Agent要根据学生的进度来进行实时反馈，就反馈不一定是说你今天做的好或者不好或者更细致的评价，而可能是动态调整当前的计划，这可能就涉及到了Agent的Heartbeat机制了，当然这是之后的事情了。”

结构化理解：未来可实验性地允许学生选择学习模型和参数，并用数学图像展示会随参数变化的计划曲线；暂不进入当前逻辑。Agent 的实时反馈重点是依据进度动态调整计划，而不是频繁评价学生表现。Heartbeat 作为后续独立议题，当前不实现。

## 核心与扩展能力（原话记录，2026-08-27）

“我觉得确实可以经常进行算法的调优，当然也可以进行独立的安装与注册新的能力，但是一些核心的设计，就比如你说的这些，是不容更改的。我说的更多可能是功能上面的改进，比如说支持一些特色功能，比如跨学科，如何从一个知识点学到另外一个看起来风马牛不相及的知识点，找出它们的联系。我只是随便举了两个例子，这些新的实验性的功能，它们可以具有自己的视图以及自己的功能，但它们都是在原有的基础上进行开发的。它们也可以提供自己的CLI供Agent调用来进行修改，但是已有的我们前面已经讨论过了，这些基本的功能是无法被取代的，也无法被删除、修改和拓展。当然，除非我们现在正处于开发阶段，所以优化它们是没有问题的。”

结构化理解：核心数据、学习记录边界、基础工作台和既有契约保持不可替代；算法调优、特色功能、独立视图和供 Agent 调用的 CLI 属于可安装/可注册的扩展层。扩展只能建立在核心之上，不能删除、替换或绕过核心能力。开发阶段仍可直接优化核心，但进入稳定使用阶段后应冻结其契约。

“目前我暂时不支持联动，因为我也没想到有什么好的联动方法。个人想到的比较可执行的一点的就是这些实验性的功能可以通过Agent来进行一些信息的交换，以此间接建立联动吧。但是归根到底都是Agent操作各自的CLI来进行独立维护。如果说agent开发中的 cordis 框架目前有什么先进的插件思想的话，说不定以后还可以用得上呢。”

决定：当前不建立插件之间的直接联动契约。实验插件各自独立维护自己的 CLI 和数据；需要交换信息时，由 Agent 在明确上下文中读取、转述或调用各自 CLI，形成间接协调。Cordis 的插件思想暂作参考，不现在引入依赖或照搬。

“我同意的，而且他们应该跟那个知识点、还有练习、还有知识图谱这三个界面平行，就是他们也可以作为第四、第五、第六个界面，然后剩下的我都同意你的想法。”

决定：实验插件启用后，以与“知识点 / 练习 / 知识图谱”平行的独立页面出现，作为第四、第五、第六个入口；默认不侵入核心页面。插件结果可以供 Agent 使用，但不强制常驻主界面。

“同意。”——确认插件安装与启用分开，启用范围按具体工作区隔离。

“可以由Agent和学生自己决定，当然这个生态目前还不存在，因为我们连本体都还没有开发完，所以这个先不管它。”

决定：插件安装权限、安装流程和生态治理暂不设计。未来可由学生或 Agent 共同决定是否安装，但等核心本体完成、确有插件生态后再另行讨论。

## 练习模式与 AI 生成边界（原话记录，2026-08-27）

“我个人的想法是可以根据所制定的一些阶段性目标或者长期目标，让学生手动选择。虽然说每次都让学生手动选择然后再生成会麻烦一点，但是这样子才是能让选择权高度掌握在学生手中的。不过其实还有一些问题，就是只要是AI生成，那就可能涉及幻觉以及难度以及考察的知识点的结构之类的，因此我个人其实并不提倡AI来生成那种大题，也就是主观题或者说非常综合的题目，只适合生成一些概念判断以及简单的选择题。也就是flash card以及yes or no的这两种题型的题目，那他们的出现又会对因为他们也是题目的一种，所以他们的加入会对题目池的结构有影响，也会对呃一些比如正确率、题目完成度、掌握度之类的也有影响，这里可能就涉及一些统计学的问题了，比如说加权。
这依然是实验性的问题，而不是防御性编程的问题。”

结构化理解：学生根据长期或阶段目标手动选择练习模式，选择权优先于完全自动生成。AI 不生成综合大题或主观题，只考虑概念判断、简单选择、Flash Card 与 Yes/No。此类 AI 题目如何进入题目池，以及怎样影响正确率、完成度和掌握判断，是需要实验权重和统计口径的测量问题，不作为普通防御性编程处理。

“我觉得可以保存进候选题的池子吧，不过因为他们是AI生成的，所以可信度会略微降低一点，就是说权重可能会低一点吧，因为他们本身也是，就算他们是可信的，他们所考察的地方也嗯不够重点。所以说他就是他们考察是那种比较基础的，所以权重本来也会呃不会那么高，不过他们还是应该保存进候选题的池子，因为他们也可以收获真实的反馈。不过我突然有点忘了，就是这也候选题的池子是正式的吗？还是说还是要经受检测的？那如何让Agent来进行验收，而让他们进入正式的题目的池子就是一个问题了。一方面是直接让Agent来审视有没有知识性错误，这没有什么可以说的。另外一方面就是检测它的难度吧，这个其实可以有一些量化指标，比如说它涉及到多少个概念之类的。当然，这个值吧，就是实验性的。顺带一提，之前以前的开发文档也讨论过如何衡量一道题目的难度吧，那些指标其实也都是实验性的。”

结构化理解：AI 生成的 Flash Card/Yes-No 保存到候选题池，作为低可信度、低权重但可获得真实反馈的题目。候选池不是正式题池，仍需经过验收才能晋升。验收至少包括知识性正确、来源或依据、题意清晰，以及难度/概念数量等实验性指标；难度指标不是既定真理，继续作为可调优的实验算法。

“agent自动晋升即可。这方面不能够让学生担心。虽然这是一件很严肃的工程，但是我依然不想让学生用户来感知这件事情。”

决定：候选题审查与晋升由 Agent 自动完成，属于系统内部内容治理；不要求学生确认，也不把门禁、审计和权重细节暴露成学习流程负担。学生只看到通过治理后可正常使用的题目和学习结果。

“我认为审查依据就不用了，但是内部来源肯定是要的。我指的不是那种每道题都有一个审查依据，而是说它材料呈现是怎么样的，或者说至少说经过最低限度的清洗和整理之后的材料是长什么样的，反正都是得留有痕迹的。当然，这个材料既然拿了进来，那肯定是过关的，没有必要删，也不能删。”

决定：不保存逐题的审查理由或审计解释，但必须保留内容来源，以及材料经过最低限度清洗、整理后的中间形态。已纳入的来源材料需要留下可追溯痕迹，不因题目后续状态变化而删除；来源保留与题目是否晋升是两个不同层次。

“你有什么意见呢？因为现在的题目池可能有一些参数是固化的，以及一些程序，所以这个我不好决定。如果可以的话，我仍然希望加入一个比较严格的去重逻辑，但是相似但不完全一样的题目依然会保留都进入池子，所以说我是尝试从新导入的材料这一部分去理解你的这个问题，而不仅仅是同一份材料再次被导入。当然这个就是一个具体的工程了，其实这个去重处理还有前面的那个审查，这两件事情都是一个工程，然后都是需要设计内部的逻辑以及对应的CI接口。嗯，这个可以事后讨论，或者说你自己拍板决定如何具体实现。”

暂定取舍：来源版本和去重不在本轮具体实现。后续把内容治理（来源、清洗、结构化、审查、晋升）与内容去重拆成两个独立工程；去重逻辑对真正重复内容严格，对相似但不完全相同的题目保留。具体 CI 接口和内部算法另行设计。

## 目标日历与每日任务配量（原话记录，2026-08-27）

“既然都说要练习某个知识点了，那题目难道不是固定的吗？呃，当然一个知识点它也可以有很多类别的题目，但是这个就应该在选择题目的那个视图那一板块里面去搞好了，这里就不应该再让用户做选择，你这里就是意义不明啊。”

“每一次练习它就只能完成一种题目。我说的一种，就是卡片、或者判断、或者综合三种中的一种。暂时暂时这么限定吧，虽然以后肯定可以更加灵活。”

结构化决定：

- 知识视图是练习范围的正式选择面，包含知识图谱和知识列表；练习页不再从全池、弱项列表或每日计划自动抓取题目。
- 学生在图谱或列表中通过明确勾选选择知识点；两种视图共享同一选择范围。点击节点或行仍然用于查看，不与加入练习混淆。
- Agent 只有在收到明确的练习意图时才可以代选；代选结果替换当前范围，不追加、不隐式改变。普通问答不能改变练习范围。
- 选择范围属于当前标签页准备状态，沿用 `sessionStorage`；不写 SQLite，不形成学习日志。关闭标签页或明确清空后结束。
- 今日计划只提供粗粒度知识范围建议；学生明确点击某项后，将该项范围带入练习启动卡，仍需选择模式。
- 练习启动卡强制选择且只选择一次综合、卡片、判断中的一种；会话期间不得混题型。没有该模式的可用题目时显示为空并让学生换模式，不自动降级。
- 现有题目只有在内容数据中显式标注后才进入卡片或判断；未标注的旧题只进入综合，不能把 `choice` 等旧题型字段擅自推断成新模式。

## 长期目标、阶段目标与 Agent 教师边界（原话记录，2026-08-28）

“刚刚忘记说长呃阶段目标和长期目标了，那些其实也是做成卡片的形式，不过呃相对会宏大一点，就不会那么精细的列出来目标。”

“如果让我选择一个动作，那必然是每天打开后的第一步行动……一个最最根本的优化方向就是尽可能多的挠到学生的痛处……一打开这个软件就能发现我接下来还有这些知识点没有过完，然后如果更好的Agent甚至已经帮我们排好了练习表，也或者说不一定是练习，也可能是更广泛的进度表，那就知道要做什么了。”

结构化决定：

- 长期目标和阶段目标与今日计划分开呈现；每个真实目标是一张相对宏观的卡片，不拆成学生必须执行的微动作。
- 目标卡默认显示标题、整体进度和 DDL；描述、范围等细节按需展开；不凭空生成不存在的目标。
- 今日计划是单独的粗粒度行动卡，最多表达少量整体推进事项，不把知识点和题目拆成操作手册。
- Agent 负责理解自然语言、选择范围、提出和调整计划；工作台负责范围过滤、题型限制、去重、练习流程、记录和调度；内容门禁负责材料可靠性。
- Agent 工作状态采用“高层状态 + 可展开产物”：默认只显示“整理中 / 审查中 / 已更新”等状态，需要时查看清洗材料、来源痕迹和变更摘要；不把 OCR、门禁和 CLI 工具日志堆给学生。
- 中间结果可以直接生效，但以有意义且可独立确认的原子批次为边界；不按每个表单制造学习日志，也不把整个长流程压成一次不可解释的写入。

本节仍属于方向讨论，不代表现有每日计划实现已获批准；在语义和数据来源收敛前，不删除 Flash Card / Yes-No 入口，也不把它们宣传为已实现模式。
