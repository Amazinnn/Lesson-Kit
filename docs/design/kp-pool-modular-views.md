# lesson-kit Design: Knowledge Pool And Modular Views

**Status:** Current v1 contract.

## Architecture

```text
Source material
  -> Pipeline extraction
  -> pool/{course}.db
  -> Views
```

The pool is a long-lived course database. Views query it and render different
student-facing artifacts.

## Storage

- One SQLite database per course: `pool/{course}.db`.
- Runtime database files are gitignored.
- Markdown intermediate files remain available for audit and repair.
- Python scripts use stdlib `sqlite3`.

## Tables

### `knowledge_points`

Persistent knowledge assets.

```sql
CREATE TABLE knowledge_points (
    kp_id           TEXT PRIMARY KEY,
    knowledge_item  TEXT NOT NULL,
    graph_label     TEXT,
    source_location TEXT,
    knowledge_type  TEXT NOT NULL,
    related_kp_ids  TEXT,
    importance      TEXT NOT NULL,
    learning_action TEXT,
    body            TEXT,
    difficulty      INTEGER CHECK (difficulty BETWEEN 1 AND 5),
    fragile         TEXT,
    created_at      TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at      TEXT NOT NULL DEFAULT (datetime('now'))
);
```

`fragile` is text: `NULL` means not marked fragile; non-null text is the
fragility note.

`graph_label` is optional short text for map-like graph nodes. It is authored
or repaired during extraction/review; renderers must not invent semantic labels.

### `problems`

Durable practice problems. A problem's durable identity is the problem itself;
source-specific pools are logical filters over `source_kind`.

```sql
CREATE TABLE problems (
    problem_id   TEXT PRIMARY KEY,
    kp_ids       TEXT NOT NULL,
    problem_text TEXT NOT NULL,
    solution     TEXT,
    problem_type TEXT NOT NULL,
    source_kind  TEXT NOT NULL,
    created_at   TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at   TEXT NOT NULL DEFAULT (datetime('now'))
);
```

Required enums:

```text
problem_type:
calculation | proof | modeling | explanation | experiment |
design | application | counterexample | other

source_kind:
textbook | quiz | midterm | final | makeup | other
```

Rules:

- `problem_id`: `{course}-{chapter}-prob-{NNN}`.
- `kp_ids`: JSON array with at least one existing KP ID.
- `solution`: optional. Final answers and worked explanations both live here.
- There is no separate `answer` field.
- There are no v1 fields for training target, condition axes, source location,
  or source label.

### `questions`

Legacy companion-check table retained for compatibility. It is not the v1
durable problem pool.

### Progress Tables

`kp_progress` and `question_progress` remain for existing learning-state flows.

`problem_progress` stores the current state of a durable problem:

```sql
CREATE TABLE problem_progress (
    problem_id TEXT PRIMARY KEY REFERENCES problems(problem_id),
    status     TEXT NOT NULL DEFAULT 'new',
    note       TEXT,
    updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

Allowed `status` values:

```text
new | wrong | stuck | reviewing | mastered
```

`problem_attempts` is append-only history for each recorded interaction:

```sql
CREATE TABLE problem_attempts (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    problem_id TEXT NOT NULL REFERENCES problems(problem_id),
    status     TEXT NOT NULL,
    note       TEXT,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

## View Relationship

- Knowledge guide view consumes `knowledge_points`.
- Problem-set view consumes `problems` and `knowledge_points`.
- Knowledge graph preview consumes `knowledge_points`, `problems`, and
  problem progress. It shows problem IDs and short problem text, not solutions.
- Editable graph view may update `knowledge_points.body`,
  `knowledge_points.fragile`, and problem progress only.
- Temporary companion checks may be generated by a view, but they are not
  durable problems.
